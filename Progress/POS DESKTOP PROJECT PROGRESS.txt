POS DESKTOP PROJECT PROGRESS
Last Updated: 2026-05-16

1. Current Status
- Desktop POS application built with Python + PyQt6.
- One main PosMainWindow with QStackedWidget-based navigation.
- Left sidebar exposes dashboards, POS Terminal, Product Management, and admin pages according to permissions.
- Runtime database: SQLite file pos.db.
- Current major areas:
  + Login, session persistence, logout.
  + POS Terminal, payment, receipt preview.
  + Product Management.
  + Admin: users, registers, reports, audit logs, settings.
- Shared refresh flow is handled through app_data_changed.

2. Recently Completed Changes
- Old: the app briefly used sold-barcode removal as a proxy for inventory.
  New: barcode is stable product identity and stock_qty is the inventory source of truth.
  Changed: removed sold-barcode deletion from the sale flow; sales now reduce stock_qty only.

- Old: already-sold barcodes could be scanned again.
  New: unavailable/out-of-stock barcodes are blocked immediately.
  Changed: validation added on scan, before payment, and again inside the database sale transaction.

- Old: scanning the same barcode twice was blocked.
  New: scanning the same barcode again increases product quantity.
  Changed: cart logic now merges by product_id, matching fixed product barcodes plus quantity-based inventory.

- Old: Shift+F5 refreshed silently.
  New: reset shows visible success feedback.
  Changed: added reset toast animation and status-bar message.

- Old: closing the app required a new login next time.
  New: session can persist across app restarts.
  Changed: added stored session recovery using the existing “Keep me logged in” toggle.

- Old: no logout action existed.
  New: sidebar includes Logout.
  Changed: added logout icon/button, session clearing, and return-to-login flow.

- Old: receipt preview could appear before payment fully completed.
  New: receipt is created/displayed only after successful payment completion.
  Changed: payment flow now waits for accepted dialog result before finalizing and showing receipt.

- Old: Manager Dashboard displayed static startup values and did not refresh after new sales.
  New: Manager Dashboard reloads through the global refresh flow.
  Changed: added dashboard reload behavior and connected it to app-wide refresh.

- Old: dashboards could miscount "today" because created_at is stored in UTC while the UI is read in local time.
  New: Admin, Manager, and Cashier dashboards use consistent local-day calculations.
  Changed: date filters now use date/datetime(created_at, 'localtime') to avoid midnight boundary drift.

- Old: Product Management used split-screen form + table.
  New: main page is list-focused and Add/Edit use modal dialogs.
  Changed: removed the left Product Details panel and added reusable ProductDialog.

- Old: update/delete depended on shared form state and current selection.
  New: each table row has its own Edit/Delete actions.
  Changed: row action buttons were added; modal edit pre-fills old data; table reloads after save/delete.

4. Global Refresh Flow
- PosMainWindow exposes app_data_changed = pyqtSignal().
- Child pages emit data_changed after database writes.
- Flow:
  page.data_changed -> notify_app_data_changed() -> app_data_changed.emit()
- Reload discovery order:
  + reload_data
  + load_dashboard_data
  + load_products
  + load_users
  + load_registers
  + load_settings
  + load_report
  + load_logs
- Shift+F5 now reloads data and shows visible reset feedback.

5. Database
- Main tables:
  + products
  + product_barcodes
  + sales
  + sale_items
  + sale_payments
  + sync_queue
- products includes barcode, sku, stock_qty, active, updated_at, image_path.
- product_barcodes supports multiple barcodes per product and primary barcode state.
- Added helper logic:
  + get_available_stock()
  + is_barcode_available()
  + was_barcode_sold()
  + ensure_sale_items_available()
- stock_qty is now the inventory source of truth.
- A one-time migration converts legacy data into the new inventory model.
- Why barcodes are not removed after each sale:
  + In ordinary retail, a barcode identifies a product type, not one unique physical unit.
  + Many identical Coca-Cola bottles can share the same barcode.
  + If one sale deleted that barcode, the next identical bottle could no longer be scanned even while stock still exists.
  + Remaining quantity belongs in stock_qty.
  + If the business later needs item-level tracking for phones, tickets, gift cards, IMEI, or serial numbers, add a separate serial_items/inventory_units model instead of overloading product barcodes.
